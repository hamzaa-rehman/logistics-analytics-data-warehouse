# Gold Layer Data Dictionary and Mapping Specification

## 1. Purpose and implementation status

This document is the approved reference for the Gold dimensional schema in the Logistics Analytics Data Warehouse. It records the source-to-target column mapping, target SQL Server data types, fact grain, surrogate-key lookups, and implemented relationship rules.

**Schema status:** The 13-table Gold schema has been deployed and its structure/constraints have been validated in SQL Server.

**Data and validation status:** The Gold full-refresh load procedure has been implemented and executed. All six fact tables have complete, unique source business identifiers, and their row counts match the corresponding Silver tables (541,172 fact rows in total). All 18 Gold foreign-key relationships passed orphan checks and are enabled/trusted; all 13 Gold primary keys are present and enabled, each with one key column. The six fact-table measure reconciliation checks also passed: 541,172 matched records, zero missing records on either side, and zero mismatches across the selected measures. The `dim_date` table contains 5,114 dates, and its ISO week-year validation returned zero mismatches and zero NULLs. The completed evidence and validation scope are recorded in [gold_validation.md](gold_validation.md). Reporting views and Power BI reporting are downstream work.

**Source of truth:** `scripts/gold/ddl_gold.sql` defines the implemented Gold columns, data types, nullability, primary keys, unique constraints, and foreign keys. `scripts/silver/ddl_silver.sql` defines the Silver source columns. If this document and the deployed DDL ever disagree, the discrepancy must be investigated and resolved; do not silently change the load scripts to fit an outdated document.

## 2. Mapping conventions and design standards

- **Surrogate key:** An integer key generated in Gold for dimensional modelling. Dimension surrogate keys use `INT IDENTITY(1,1)`; fact row keys use `BIGINT IDENTITY(1,1)`.
- **Source business key:** The original source identifier is retained in its Gold table as `VARCHAR(50) NOT NULL` and protected by a UNIQUE constraint. It supports lineage, traceability, and source-to-Gold reconciliation.
- **Dimension lookup:** A fact's descriptive relationship is stored using the relevant dimension's surrogate key, resolved by matching the source business key to the dimension's retained source ID.
- **Date key:** `date_key` is an integer in `YYYYMMDD` format. Fact date keys are derived from the relevant Silver DATE or DATETIME2 value. For a DATETIME2 source, use its calendar date; retain the original timestamp separately where the Gold table includes it.
- **NULL handling:** Preserve missing optional source relationships as NULL. Do not invent a driver, truck, trailer, customer, route, or facility key. Required Gold date keys are NOT NULL and must be validated during loading.
- **Slowly changing dimensions:** The current model uses Type 1 handling (overwrite descriptive attributes on a full refresh). The source provides current master records, not reliable historical snapshots; this design does not claim historical attribute tracking.
- **No automatic unknown member:** The deployed DDL does not define an unknown/default dimension row. A missing optional source ID therefore remains a NULL surrogate key.
- **Data types and nullability:** The types and NULL/NOT NULL declarations shown below reproduce the deployed Gold DDL.

### 3.7 `gold.dim_date`

**Source:** Generated in Gold; no single Silver source table.  
**Dimension grain:** One row per calendar date.  
**Primary key:** `date_key` (integer YYYYMMDD).  
**Unique alternate key:** `full_date`.

| Gold target column | Gold data type | Nullability | Derivation |
|---|---:|---|---|
| date_key | INT | NOT NULL | Integer representation of `full_date` in YYYYMMDD format. |
| full_date | DATE | NOT NULL | One calendar date per row. |
| day_of_month | TINYINT | NOT NULL | Day number within the month. |
| day_name | VARCHAR(10) | NOT NULL | Deterministic weekday name. |
| day_of_week | TINYINT | NOT NULL | Monday = 1 through Sunday = 7. |
| week_of_year | TINYINT | NOT NULL | ISO week number (1–53). |
| iso_week_year | SMALLINT | NOT NULL | ISO week-based year; may differ from the calendar year near New Year. |
| month_number | TINYINT | NOT NULL | Month number, 1–12. |
| month_name | VARCHAR(10) | NOT NULL | Deterministic month name. |
| quarter_number | TINYINT | NOT NULL | Calendar quarter, 1–4. |
| year_number | SMALLINT | NOT NULL | Calendar year. |
| year_month | CHAR(7) | NOT NULL | YYYY-MM label. |
| is_weekend | BIT | NOT NULL | 1 for Saturday/Sunday; otherwise 0. |

**Calendar range:** 2012-01-01 through 2025-12-31 inclusive (5,114 dates). This covers the observed source date ranges and provides complete calendar years around the operational data.

**Generation rules:** Generate one row for every date in the range. Calculate the integer key from the date. Weekday numbering and names must be deterministic and must not depend on the SQL Server session's language or `DATEFIRST` setting. Use `DATEPART(ISO_WEEK, full_date)` for `week_of_year`. Derive `iso_week_year` from the year containing the Thursday of the date's ISO week; this is calculated as `YEAR(DATEADD(DAY, 4 - day_of_week, full_date))`, where Monday = 1 and Sunday = 7. Do not combine `year_number` with `week_of_year` to create ISO week labels. Use `year_number` for calendar-year reporting and `iso_week_year` with `week_of_year` for ISO weekly reporting.

## 4. Gold fact tables — final column mapping

Fact grain is critical: each fact table represents a distinct business event or transaction. Do not join raw fact tables to one another and then aggregate their measures unless the join is first reduced to a compatible grain. Such joins can create fanout (duplicate rows caused by one-to-many relationships) and inflate totals.

## 5. Constraints and relationship rules

The deployed schema contains 13 tables: seven dimensions and six facts.

| Table | Primary key | Unique constraint / alternate key |
|---|---|---|
| gold.dim_customer | customer_key | customer_id |
| gold.dim_driver | driver_key | driver_id |
| gold.dim_truck | truck_key | truck_id |
| gold.dim_trailer | trailer_key | trailer_id |
| gold.dim_route | route_key | route_id |
| gold.dim_facility | facility_key | facility_id |
| gold.dim_date | date_key | full_date |
| gold.fact_loads | load_fact_key | load_id |
| gold.fact_trips | trip_fact_key | trip_id |
| gold.fact_delivery_events | delivery_event_fact_key | event_id |

### 5.2 Implemented foreign keys

The deployed Gold schema contains 18 foreign-key constraints, all from facts to dimensions.

| Fact table | Fact foreign-key column | Referenced dimension column | Relationship meaning |
|---|---|---|---|
| fact_loads | customer_key | dim_customer.customer_key | Load's customer. |

### 5.3 Relationships intentionally not enforced as Gold foreign keys

The following source identifiers are retained as columns for traceability, but the deployed DDL does not define foreign keys for them:

- `fact_trips.load_id`
- `fact_delivery_events.load_id` and `fact_delivery_events.trip_id`
- `fact_fuel_purchases.trip_id`
- `fact_safety_incidents.trip_id`

These are not dimension surrogate-key relationships in the deployed model. In particular, do not create fact-to-fact joins as a substitute for dimensional relationships. Where analysis needs to combine facts, aggregate each fact independently to a compatible reporting grain and then combine the aggregates.

### 5.4 Optional relationships and NULL preservation

The following fact foreign-key columns are nullable in the deployed DDL: `customer_key`, `route_key`, `driver_key`, `truck_key`, `trailer_key`, and `facility_key`. Their NULLability reflects optional or missing source identifiers. During loading:

1. If the source foreign key is NULL, load the Gold surrogate key as NULL.
2. If the source key is populated, resolve it against the appropriate dimension's retained source business key.
3. If a populated source key does not resolve, treat it as a load validation failure or explicitly reported exception. Do not silently convert an unresolved key to NULL.
4. Do not infer missing truck/driver IDs from a related trip when loading fuel purchases or safety incidents.

All fact date-key columns (seven columns across the six fact tables, because delivery events have scheduled and actual date roles) are NOT NULL. The load process must validate that each source date is populated and that the derived date key exists in `dim_date` before inserting the fact row.

### 5.6 Source tables not represented as standalone Gold dimensions or facts

The Silver tables `driver_monthly_metrics` and `truck_utilization_metrics` are monthly aggregate tables, not transaction-level event facts. They are not included as standalone Gold facts in this deployed model. Their measures must not be mixed with transaction-level fact measures without an explicit grain and reconciliation design.

## 6. Load and analytical safeguards

The following rules are part of the model's intended use and must be preserved in Gold loading, reporting views, and Power BI:

1. **Respect fact grain.** Load one row per source load, trip, delivery event, fuel purchase, maintenance record, or safety incident, respectively.
2. **Do not combine raw facts indiscriminately.** One-to-many joins between facts can multiply rows and inflate revenue, fuel cost, trip distance, maintenance cost, or incident amounts.
3. **Keep financial measures distinct.** Reported load revenue, fuel surcharge, accessorial charges, fuel purchase cost, maintenance cost, and safety claim/damage amounts have different meanings.
4. **Do not assume currency.** The source does not establish a currency for the recorded fuel, maintenance, or safety amounts. Do not label them AED, USD, or another currency.
5. **Do not overstate fleet utilization.** Trip activity and recorded monthly utilization metrics do not establish daily fleet availability. Use supported activity measures and clearly named denominators.
6. **Do not infer causation.** Observed relationships between detention and on-time status, or changes in safety rates, are descriptive findings, not proof of causes.
7. **Preserve source NULLs.** Optional source relationships remain NULL; missing identifiers must not be fabricated or backfilled from adjacent records without authoritative evidence.
8. **Validate every load.** Reconcile source and target row counts, source business-key uniqueness, dimension lookups, required date keys, NULL preservation, and key measures before treating Gold data loading as complete.
